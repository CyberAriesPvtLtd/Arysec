Security Is a Design Decision

Most of what we build is unglamorous and load-bearing: the customer portal that carries your revenue, the internal system your operations team lives in for eight hours a day, the API a partner integrates against, the integration layer keeping a twelve-year-old ERP talking to everything bought since. We work in mainstream stacks, not fashionable ones, because you have to hire for this codebase after we leave. In practice that usually means TypeScript and React on the front end, Node.js, Python, Java or .NET services behind it, PostgreSQL or SQL Server where the data matters, and deployment onto AWS, Azure or your own servers depending on where your obligations sit.

The difference between us and a general development firm is where security enters the project. In most builds it arrives at the end, as a penetration test three weeks before launch producing findings nobody has time to fix properly. We put it at the start. Before implementation we build a threat model: data flow diagrams for the system, STRIDE analysis on each trust boundary, abuse cases written alongside user stories, and security requirements drawn from OWASP ASVS at the verification level the system's risk justifies. Authentication, session handling, authorisation logic, input validation, output encoding, cryptography and logging get designed rather than retrofitted. Credentials never live in source: secrets sit in a managed vault such as HashiCorp Vault, AWS Secrets Manager or Azure Key Vault, are injected at runtime, and repository history is scanned so a key committed by accident is caught in minutes, not months later by somebody outside the company. Our pipeline practice follows the NIST Secure Software Development Framework in SP 800-218, and we assess wider engineering maturity against OWASP SAMM where you want that view.

You own everything at the end. Code lives in your source control from the first commit, not ours. Infrastructure is defined as code in the same repository, so environments are reproducible instead of remembered. Handover includes architecture decision records explaining why choices were made, an OpenAPI specification for every service interface, runbooks for the operational tasks, and a working session with whoever inherits the system. We do not embed proprietary components only we can maintain, and we will tell you plainly when a requirement is better met by an existing product than by code we write for you.

How It Works

Our Engagement Process

How a Software Development engagement runs from first conversation to steady state.

01

Discover and Model

We work through requirements, data classification and integration points, then build the threat model and agree the security requirements. Scope, architecture and acceptance criteria are written down before anyone opens an editor.

02

Build in Sprints

Development runs in two-week iterations with a demonstrable increment at the end of each. Every merge request gets peer review, a security-focused check against the ASVS requirements, and an automated scan set.

03

Test and Harden

Functional and integration tests run continuously. Before release the application goes through dynamic testing and an independent assessment by a tester who did not write the code, with findings fixed before launch.

04

Release and Support

Deployment follows a rehearsed runbook with a rollback path. Documentation and credentials transfer to your team, warranty covers defects for an agreed period, and you choose whether we stay on retainer.

We are useful in three situations: your team is at capacity and a dated commitment is slipping, the work needs a skill they do not have and will not need again, or you want secure development practice established and then handed over. In the third case the deliverable is partly the pipeline, the threat modelling habit and the review standard, not just the software. We are happy to work inside your process, not beside it.

The design stage is longer and the delivery stage is shorter. A threat modelling workshop takes a day or two; retrofitting authorisation logic after a test finds tenant data leaking takes weeks and often forces a schema change. Automated scanning adds minutes to a build, not days. The real extra cost is on the first project, because we are also setting up pipelines and standards that later work reuses. At scoping we will say which controls are proportionate to the system's risk.

You own it. Under a retainer we monitor advisories affecting your specific bill of materials.
